# נוהל שחרור גרסה

**חוק על:** אחרי כל שלב — לעצור, להראות מה נעשה, ולחכות לאישור.
אין הרצה של שני שלבים ברצף. "תמשיך" הוא אישור לשלב אחד בלבד.

---

## שלב 0 — מה בכלל נכנס לגרסה

```
git status --short
git diff --stat
```

**להציג את הרשימה ולשאול איזה קבצים שייכים לשחרור הזה.**

אם יש שינויים שאינם שייכים — עבודה שממתינה לבדיקה, ניסוי באמצע,
קובץ שנשכח — **לעצור ולשאול**. לא להניח שכל מה שמשתנה מיועד
לצאת.

הרשימה שהמשתמש אישר כאן היא הרשימה שתיכנס ל-`git add` בשלב 5.
**אף פעם `git add -A` ו-`git add .`** — הם סוחפים בדיוק את מה
שהמשתמש לא בדק.

⏸ אישור לפני שלב 1.

## שלב 1 — אין שגיאת parse

מחלצים כל בלוק `<script>` שאין לו `src` ומריצים עליו `node --check`:

```bash
node -e '
const fs=require("fs"),vm=require("vm");
const h=fs.readFileSync(process.argv[1],"utf8");
const re=/<script(?![^>]*\bsrc=)(?![^>]*\btype="(?!text\/javascript)[^"]*")[^>]*>([\s\S]*?)<\/script\s*>/gi;
let m,n=0,bad=0;
while((m=re.exec(h))){
  n++;
  const line=h.slice(0,m.index).split("\n").length;
  try{ new vm.Script(m[1]) }
  catch(e){ bad++; console.log("בלוק "+n+" (שורה "+line+"): "+e.message) }
}
console.log(n+" בלוקים נבדקו, "+bad+" נכשלו");
process.exit(bad?1:0);
' index.html
```

`type` שאינו `text/javascript` מסונן — בלוק JSON אינו קוד ואינו
אמור להיבדק ככזה.

**אם יש שגיאה — עוצרים כאן.** לא "נתקן תוך כדי". קובץ שלא נטען
לא משוחרר.

⏸ אישור לפני שלב 2.

## שלב 2 — BUILD ומפתח המטמון, לאותו ערך

שני מקומות, ולעולם לא אחד בלי השני:

1. `BUILD` ב-`index.html`
2. מחרוזת הגרסה ב-`sw.js?v=...` שבקוד הרישום

ולוודא ש-`sw.js` בונה את `CACHE` מ-`?v=` ולא מקבוע משלו — אחרת
העדכון לא יגיע גם כשהמספרים תואמים.

**להראות את שתי השורות זו מתחת לזו** לפני שממשיכים:

```
index.html:562   var BUILD="v58 · 2026-08-29";
index.html:2916  navigator.serviceWorker.register("sw.js?v=v58");
sw.js:9          const CACHE = "app-" + V;
```

חוסר התאמה כאן פירושו שמי שכבר התקין את האפליקציה יקבל את הגרסה
הישנה — התקלה הכי קשה לאבחון, כי בדפדפן של המפתח הכול תקין.

⏸ אישור לפני שלב 3.

---

## שלב 3 — בדיקה שהגרסה באמת עובדת

*(המשתמש לא הגדיר את השלב הזה. זו ההשלמה שנבחרה — אם הוא התכוון
למשהו אחר, לשאול ולעדכן את הקובץ.)*

לפחות אחד מאלה, לפי מה שקיים בפרויקט:

- אם יש `tests/` — להריץ, ולהראות כמה עברו וכמה נכשלו.
- אם אין — לטעון את הדף, לוודא שהמסך הראשי מצייר, ושמספר הגרסה
  שמוצג הוא **החדש**. זו הבדיקה שמוכיחה ששלב 2 באמת נתפס.
- אם השינוי נוגע להקראה — להשמיע משפט אחד ולשמוע אותו.

**לדווח תוצאה אמיתית.** מבחן שנכשל נאמר עם הפלט שלו, לא מסוכם
כ"בעיקר עובד".

⏸ אישור לפני שלב 4.

---

## שלב 4 — CHANGELOG

**נכתב לפני הקומיט, לא אחריו** — כדי שהוא ייכנס לאותו קומיט
כפשוטו, בלי `--amend` ובלי לגעת בהיסטוריה שכבר נדחפה.

אם `CHANGELOG.md` אינו קיים — ליצור אותו, עם כותרת ושורה שמסבירה
שסימן הגרסה באפליקציה משמש גם כמפתח המטמון.

רשומה חדשה בראש, בפורמט שכבר קיים בקובץ:

```
## v58 - כותרת קצרה בגוף ראשון של המשתמש

מה השתנה מנקודת מבט מי שמשתמש באפליקציה. לא שמות פונקציות,
לא מספרי שורות.
```

**להציג את הרשומה ולקבל אישור על הניסוח** לפני שמקמטים.

⏸ אישור לפני שלב 5.

## שלב 5 — commit ו-tag

```
git add <רק הקבצים שאושרו בשלב 0, מפורשים בשם>
git commit -m "<תיאור>"
git tag good-v58
```

מספר התגייה הוא **אותו מספר** של `BUILD` משלב 2. לא חדש, לא +1.

התגייה היא נקודת השחזור. משם אפשר להחזיר קובץ יחיד בלי לגעת
בשאר:

```
git checkout good-v58 -- index.html
```

**לוודא שהתגייה נוצרה** לפני שממשיכים:

```
git tag | tail -3
```

⏸ אישור לפני שלב 6.

## שלב 6 — push

```
git push -u origin <branch>
git push --tags
```

`--tags` היא פקודה נפרדת. בלעדיה התגייה נשארת מקומית, ונקודת
השחזור לא קיימת בשום מקום אחר — וזה בדיוק המצב שגילינו שקיים
היום: אפס תגיות בשני הריפו.

לתת קישור, ולהזכיר ש-GitHub Pages לוקח דקה או שתיים עד שהשינוי
חי. לא להסיק שהשחרור נכשל לפני שעברו.

## אסור, בלי יוצא מן הכלל

- `git add -A` או `git add .` בנוהל הזה.
- `--amend` על קומיט שכבר נדחף.
- `push --force` או `--force-with-lease` כחלק מהנוהל.
- להזיז תגייה שכבר קיימת בשרת.

אם נוצר מצב שנראה כאילו הוא דורש אחד מאלה — **לעצור ולשאול**.
כמעט תמיד יש דרך קדימה: קומיט תיקון חדש ותגייה חדשה.
